# Cangjie 调试技能

本 skill 由同一份模板加 Cangjie 插槽展开，可独立加载：建立会话、检视、改值、追踪与剖析的指引都在本文件内，不需要再读其他 skill。

## 1. 触发信号

- 仓颉程序崩溃（段错误或异常退出），栈帧落在编译产物而不是源码行。
- `Option<T>`、class/struct、泛型实例显示成底层字段，看不出业务含义。
- 断点显示未生效，或变量读不到、疑似产物没带调试信息。

## 2. 前置条件

- 用 `cjc -g` 编译；不带 `-g` 时只有地址与符号名。
- cjc 在 PATH（或 `LANGDEBUG_CJC` 指定），且 lldb-dap 可用；两者缺一都判为后端不可用。
- 产物不要 strip：符号被去掉后栈帧只剩地址。
- 源码路径要在会话 `cwd` 下能解析，断点按文件基名匹配。

## 3. 建立会话

1. 先 `debug_env` 探测：确认调试器或适配器可用、版本可识别，并记下缺失项与安装建议。
2. `debug_session` 建立会话：launch 由工具注入调试参数，attach 复用已有调试端口；记下会话标识。
3. `debug_breakpoint` 设置断点，优先使用条件或命中序号，断点数量保持少量。
4. `debug_run` 的 continue/until 做一次性闭环：命中后同一响应里拿到位置与变量值。
5. 需要更多变量时 `debug_inspect` 批量取；需要改值时 `debug_mutate`，旧快照随即作废。
6. 结束时 `debug_session` 关闭会话。

- 启动命令给 cjc 编译出的可执行文件路径：`["./bin/app","--flag"]`；`cjc`、`cjpm` 不是可执行目标，会被拒绝。
- 只支持 launch（lldb-dap 托管目标）；attach 未实现，常驻服务只能由工具 launch，或另存带符号产物离线分析。
- 入口停在目标启动处，业务帧要等断点命中才有；先设断点再继续执行。
- 后端优先 lldb-dap，缺失时降级 gdb MI：此时只有断点、栈与变量读取，改值、logpoint 与 `>N` 命中序号不可用，改用 `debug_eval`。

## 4. 工程化项目

本工具不代跑构建，也不解析 `pom.xml`、`build.gradle`、`CMakeLists.txt`、`Makefile`、`build.sbt` 或 `package.json`：构建由你或 CI 先完成，会话只消费产物。

1. 用工程自己的构建命令产出带调试信息的产物：Debug 配置、保留符号、不要 strip、不要开高优化。
2. 找到该构建工具实际写入的产物路径（class 目录、jar、可执行文件或构建后的 JS），把它作为 `debug_session` 的启动命令，而不是构建工具本身。
3. 多模块/多包工程里，`cwd` 要与产物和源码的基准目录一致；命令中的相对路径都按 `cwd` 解析。
4. 需要在构建工具内部调试（跑测试、跑 `run` 任务）时，让构建工具以等待调试器的方式启动，再用 attach 连它的端口。
5. 构建描述文件里读不到的调试信息（classpath、sourcemap、`-g`）要显式确认，缺失时先补构建配置再排查代码。

- 直编：`cjc -g -o bin/app src/main.cj`；工程用仓颉包管理器（cjpm）时先完成构建，再把产物路径交给会话。
- 工具不代跑 `cjc`/`cjpm`，也不解析工程文件：构建报错先自己解决，不要在会话里等。
- 调试产物要 `-g`、不开高优化、不 strip；发布产物通常被 strip，不能用来定位变量。
- 多包工程把 `cwd` 设在工程根，断点用绝对路径，避免相对路径落到别的包。
- 缺符号时工具会拒绝会话并提示用 `-g` 重编，按提示重建后再建会话。
- 产物路径随构建方式变化（`bin/`、`build/`、`target/`），以工程实际输出为准。

## 5. 读值陷阱

- class 是引用语义，调试器里是指向堆对象的指针；struct 是值语义，按字段直接展开。
- `Option<T>` 是枚举：先看判别字段再读 payload，直接当普通结构体读会得到无意义的值。
- 字符串是对象（指针 + 长度），不是 C 字符串；按长度读，不要按 `\0` 截断。
- 泛型实例的类型参数出现在符号名里，同名函数的不同实例是不同帧。
- 内联与优化会折叠帧，栈上看到的是调用方；只有 `-g` + 不优化才稳定。
- 仓颉程序的标准输出与调试器输出可能交错，按时间戳对齐再看日志。

## 6. 改值边界

- 改值受 lldb-dap 能力限制；gdb 降级时写值不可用，报错后不要反复重试。
- class 字段写入影响所有引用同一实例的地方，改前确认没有共享。
- struct 是值类型，改栈上副本不影响已传出的参数。
- 枚举判别字段改动会让 `Option` 状态与 payload 不一致，后续匹配可能走错分支。
- 只读数据（字符串字面量、常量）写入会触发 `SIGSEGV`。

## 7. 高频反模式

每条反模式按固定格式记录：**现象 → 误判 → 正确做法**。

- **现象**：崩溃栈只有地址或 `??` → **误判**：以为调试器坏了 → **正确做法**：先确认 `cjc -g` 且产物未 strip。
- **现象**：`Option` 值看起来是乱码或底层字段 → **误判**：以为变量被写坏 → **正确做法**：按枚举判别字段 + payload 展开，不要按普通结构体读。
- **现象**：变量显示 `<optimized out>` → **误判**：以为内存被踩 → **正确做法**：优化构建里这类值不可恢复，换 Debug 产物复现。

## 8. 性能分析

- native 侧用采样式剖析（perf 等），需要 `-g` 与保留帧指针，按符号归并热点。
- 仓颉没有专用剖析器时，用采样 + 断点计数交叉验证，结论里标注采样性质。
- 采集点与栈采样的可用性以 `debug_env` 返回的 capability 清单为准；清单没写可用时不要声称已采集。

## 9. 流程纪律

1. 任何调试动作之前先探测环境；调试器缺失时先返回安装或开启指引，不要硬建会话。
2. 默认少量精确断点（一般 1–3 个），用条件或命中序号约束；不得以单步执行替代采集。
3. 在可能高频执行的位置设置采集点前，必须先设定速率上限或采样率。
4. 断点选「能观测到问题的最早位置」，不要一路下到用户报告的行号再回看。
5. 同一轮排查复用同一份快照标识；快照失效后重新停止再取，不要混用改前与改后的值。

## 10. 结论输出规范

给出结论时必须提供证据三元组：

- 位置：文件与行号，例如 `src/handler.py:42`。
- 观测值：该位置实际取到的值及其路径，例如 `locals.retries = 3`。
- 复现路径：从启动到该观测的最小步骤（会话模式、断点条件、运行动作）。

不得仅凭代码阅读下断言。尚未取得运行态证据时，写成「待验证假设」，并给出下一处要停下的位置。

## 11. 收尾

1. 调试结束关闭会话，释放后端进程与监听端口，不留下后台调试器。
2. 若本轮改过值，结论中标注目标进程内存已被修改，后续行为可能偏离原始逻辑，需要重启才能恢复。
3. 保留用过的断点与快照标识，便于他人复现。
